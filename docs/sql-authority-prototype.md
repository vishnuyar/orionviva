## Existing behavior and options

Current SQLCipher is disposable derived state; encrypted JSONL is financial authority (ADR-015 and local-first storage design). T4 means every change is append-only and hash-chained, current state is derived, and chain checking needs no key. PROG-45 additionally requires full physical validation on canonical decisions; warm-open freshness is weaker. SQLCipher alone does not reproduce these guarantees. The existing connector uses DELETE journaling, FULL synchronous and memory temporary storage. WAL is not the implemented policy.

Current capture saves originals before reading and, when acquisition/model/phase metadata is available, receipts before settlement; a metadata-free offline reading does not unconditionally create such a receipt. The prototype must always persist its own immutable extraction receipt. Settlement invokes financial-family projectors and cross-document healing; investment validation traverses historical events and prefixes. Existing StatementFacts, Decimal arithmetic, account-kind rules and pure posting constructors are reusable. Identity resolution and historical value-time semantics are more substantial than label matching or filtering latest rows. These claims require independent factual review before implementation.

Continuing the current log-backed design preserves compatibility but does not test the chosen architecture. Immediate production replacement would reopen audit, backup, keyless verification and recovery before equivalence is shown. Recommend a separate SQL-authoritative prototype with one complete first financial slice, then verified coverage expansion before migration. Isolation is reversible; production migration is a sticky decision after proof.

## Data and transactions

Use one private SQLCipher authority database plus immutable encrypted source blobs. Entities cover format/schema version, documents, immutable extraction receipts, staged statements/rows, validation runs/findings/dependencies, accounts, periods/balance observations, transactions/postings, append-only audit events/commits, and durable import items. Retain original responses, reader/prompt/profile/normalization identities, fact/posting provenance and deterministic idempotency keys. Accepted staging evidence stays immutable; promotion creates accepted records referencing it. Later corrections append decisions/reversals.

Money uses exact Decimal text, never SQLite REAL or float SUM. Index account identity, account/period, document/extraction contract, posting identities and affected pending dependencies. Reconsider only pending items whose dependencies changed. Do not infer account identity from a label or the model's selected account.

Persist the encrypted original before extraction and its response receipt before completed extraction. Reading runs outside financial transactions. Uncertain external requests cannot automatically repeat; resume retained settlement without another reading. Reuse pinned KDF policy and fail-closed SQLCipher, restrict paths, and test ciphertext/side files. All staged facts are encrypted.

Settlement acquires a write transaction, reads current revision and indexed dependencies, validates, appends audit decisions, inserts accepted records/provenance, persists findings/import completion, advances revision and commits together. If validation is outside that transaction, recheck its complete versioned read-set under the write transaction; a process mutex is insufficient. Unique constraints prevent duplicates, including retry after lost acknowledgment. Rollback leaves no partial accepted state. Use DELETE journaling, FULL synchronous and memory temp initially; WAL is outside this first fence.

## Integrity and format boundary

SQL audit events contain sequence, previous hash, sealed payload and source bindings; commit envelopes share the financial transaction. API updates/deletes are forbidden. Explicit verification independently reconstructs accepted state from audit, detecting direct accepted-table changes and audit reorder/delete/modification/truncation against the retained commit/head. Export sealed records, chain, boundaries, source hashes and a MAC-authenticated head. Passphrase-free checking verifies structural chain consistency only; authenticating the head MAC requires the key, and establishing completeness additionally requires a trusted expected head. Coherent replacement with an older vault/export and external anchoring are not demonstrated. Export is a verification artifact, not keyless access to the encrypted live database. Do not dual-write a second canonical JSONL log or claim cross-file atomic head durability without a proven recovery protocol.

Use a new explicit format such as `viva-sql-authority-prototype-v1`; refuse legacy roots, unknown formats and unsafe paths. The legacy app never auto-opens/upgrades it. Ordinary writes/current reads must not construct or invoke EventStore, Ledger, LedgerProjection, `_settle_read`, whole-history reconstruction from SQL audit or old global healing. Trap actual constructors/financial entry points, private-vault/environment access and unbounded SQL/history consumption; a module-import ban is not the test. Replay is allowed only for explicit verification, recovery and independent comparison.

A production switch requires a reviewed ADR replacing the storage-specific portions of T4, PROG-45 and ADR-015 while preserving capture, provenance, math, immutable measurements and privacy. If a final design weakens an integrity guarantee, the owner decides that concrete tradeoff before migration. No further owner decision is needed for this isolated prototype.

Before production migration: verify backup, migrate into a new root, preserve source/event/historical identities, compare complete financial/audit state, reopen/verify, then consider switching. Rollback before adoption returns to the untouched original. After new-format writes, rollback needs explicit export/reconciliation; the old root cannot contain those writes. No personal vault participates.
