# Account Connection Research — getting bank, card, and brokerage data with the user's authorization

**State:** design-only
**Rules:** none

## Rules

No connector exists in the tree, and this document is a pre-decision survey with four forks still open. Its normative content is positions to argue with, recorded under *Why*, and the work items are under *Open*. Nothing here is a rule a test can hold the code to yet; the first rules arrive with the evidence-class design named as item 1 of the sequence.

## Why

For users comfortable authorizing it, the product should be able to receive bank, credit-card and brokerage data directly from the institution — the way tax software imports a tax form — rather than relying only on manually dropped statements. The constraint that shapes everything: this is open source and runs entirely on the user's device. There is no company, no backend, and no ability to sign the business-to-business data-access contracts that power aggregator-style products. Whatever mechanism is chosen, the *user* holds the relationship and, where there is a cost, pays for it — and every byte that leaves the machine must be visible.

**Two findings reframe the question before any option is weighed.** First, the tax-software import people picture is not an open mechanism: each institution stands up a private endpoint under a bilateral contract with one vendor, and payroll data is bulk-uploaded into that vendor's own data centre before filing season. The protocol is standard; the access is contractual and closed, and no third party can join it. So the goal is not to use what tax software uses — it is to recreate that *experience* through mechanisms an individual can authorize alone.

Second, the last three years have been a controlled experiment in what survives, run by the open-source finance community. Every free business-tier that self-hosted apps depended on died: one aggregator's free development environment, another's free tier, a third's free European service. What survived and grew was services the **user pays for directly**, **open protocols** with multiple implementations, and **institutions' own individual-developer programs**. Three independent open-source personal-finance projects converged on the same answer, and that convergence is the strongest single signal in this document.

**The regulatory backdrop matters more than usual.** The US consumer data-rights rule that would have mandated free API access and banned screen scraping is not in effect: it was moved against, enjoined, its first compliance date passed unenforced, and a rewrite is in review that is expected to *permit* banks to charge for data access while keeping the API mandate. Realistic enforceable compliance is years away and likely followed by fresh litigation. Meanwhile banks moved unilaterally — one measured 1.89 billion aggregator pulls in a single month with only about 13% user-initiated, began charging aggregators, and signed a paid access deal; another blocks third-party credential sharing outright and routes programmatic access through a bank-owned network; a core provider is phasing screen scraping off a platform serving hundreds of community banks.

Three consequences follow. The era of free, scraped US bank data is closing, and anything built on it inherits a negative trajectory. Models where the **user pays** and pulls are **user-initiated** are the regulatory-safe direction, which is exactly the direction this product's constraints force anyway. And the one durable local-first gift inside the rule, in both versions, is that data providers must give **consumers themselves** electronic access to their own data — which produces *files a user downloads*, flowing naturally into a watched folder. The no-middleman future, if it arrives, arrives as better downloads rather than as open APIs for unregistered apps.

**The option landscape has four families.** Commercial aggregators where the product holds the contract are structurally unavailable — there is no company to sign, and routing data through a product-operated server would break the privacy promise anyway. They matter here only because their capabilities define what users expect, two are reachable indirectly through user-pays doors, and their statement-PDF products prove banks can serve the exact artifact the ingestion pipeline already reads. **User-pays bridges and open protocols** have the user subscribe personally, the bridge hold the aggregator relationship, and the app speak an open protocol using a token the user pastes in — no developer contract, no developer payment, app-side code fully auditable. This is where the open-source ecosystem landed. **Bring-your-own-credentials** has the user sign up for a developer or individual tier themselves; a proven pattern, in tension with the install-an-app skill bar. **No middleman at all** — watched folder, direct-connect protocols, browser-extension statement harvesting, email triggers — has the strongest privacy and provenance and the weakest automation coverage, with one large exception.

The user-pays bridge is the standout: an open, read-only, four-endpoint protocol with a hosted implementation that proxies a major aggregator, so an individual buys aggregator-grade connectivity for a few dollars a month with no aggregator contract. Credentials go to the aggregator's vetted handling and never touch this product; the user generates a setup token and pastes it in; the app claims it once, and a second claim attempt fails loudly, which is a useful tamper signal. What makes it the standout is who else chose it — several independent self-hosted projects, including hardcore privacy users who accepted it after a third-party security audit — and that the protocol now has a second independent commercial implementation serving other regions. One client implementation reaches both bridges and any future one: the protocol has crossed from one company's API to a small open standard, which is exactly the kind of dependency an open-source project can afford. Its weaknesses, stated honestly: thin investment data, no statement PDFs, data transiting two intermediaries, and a small operator — though the open protocol is precisely the hedge against the last of those.

Bring-your-own-keys buys the best data breadth available, including investments, liabilities and bank-branded statement PDFs for a substantial share of depository accounts. It cannot be the default path: it fails the install-an-app bar by construction — dashboard signup, API keys, a security questionnaire, months-long per-institution waits — and individual terms have been changed adversely before, recently. It is worth supporting for users who can walk it. The easiest bring-your-own signup in the industry connects via banks' own mobile-app APIs rather than scraping, but requires each user to manage a client certificate, covers only banks and cards, and returns no documents.

Brokerages turn out to be more open to individuals than banks. One major brokerage runs a real individual-developer program giving a retail customer accounts, balances, positions and transaction history, free and officially sanctioned — the single best direct, no-middleman feed from any major US institution. A brokerage-side aggregator offers self-serve read-only access across many platforms free for personal users; another broker offers scheduled, user-defined activity reports fetched with a personal token, very close in spirit to a statement. Two large brokerages offer individuals nothing programmatic, and the watched folder covers them.

The old direct protocol — the user's own bank login, structured responses served by the bank itself — is in terminal decline at majors but survives at hundreds of community banks and credit unions, and one card issuer reinstated it. A client is days of work with an existing library; the cost is that the community institution directory is defunct, so the project must curate its own registry and accept per-bank quirks and overnight shutoffs. Worth shipping cheaply, never promised for major banks.

**The document routes deserve more respect than "fallback"** because they are the only ones that deliver the actual statement documents — the artifact the whole provenance pipeline is built around and the strongest evidence class the product has. The watched folder is universal: every institution offers statement PDFs plus some tabular export, and the community has already solved format chaos once with a crowd-sourced registry of 124 bank-format configs, which is a data-driven, community-contributed model that fits this project's no-hardcoding rule exactly. Its cost is user discipline, monthly, and that cost can be engineered down. Email notifications rarely contain the PDF, so mail is not a document source — but read locally, with the user's own credentials never leaving the device, it is an excellent freshness and completeness signal: the product learns a statement exists before it has seen it, which turns a quiet incompleteness state into a precise, timely one. A companion browser extension is materially different from headless scraping: the user is already logged in, with MFA passed and a genuine device fingerprint, and the extension automates *the user's own attended session* rather than storing credentials and impersonating a browser, so bot detection largely does not trigger and the legal posture is far cleaner. It is the only mechanism in the entire landscape delivering the tax-software experience *and* the strongest evidence class *and* no middleman — and the most expensive to sustain, viable only as a community-maintained recipe registry and never as a core-team obligation to keep N banks working.

**What is structurally closed** is worth knowing: the enterprise-contract aggregators have no individual tier and no plausible one; the de facto open-banking wire format publishes its spec royalty-free while every bank's endpoint sits behind bilateral, security-vetted, increasingly paid recipient agreements — so building a *parser* is cheap future-proofing and expecting *endpoint access* is not realistic on any horizon here. Headless screen scraping of US majors is a dead end: no maintained library, enterprise-grade bot detection, banks actively closing it, and a bundled credential-storing scraper would be the one automation route that genuinely deserves the label this product forbids.

**Internationally**, the pattern worth encoding is that every region eventually offers either a user-pays bridge, an own-accounts free tier, or neither — and the document routes work everywhere. Europe's famous free tier is winding down and its replacement is an explicitly sanctioned free restricted mode for individuals on their own accounts; one large market's aggregator framework is licensed and business-only with no individual tier, so the watched folder is that region's story; smaller markets have their own free personal tiers.

### What connected data means for the trust model

This is where the real design work lives; everything above is plumbing.

**A feed is a new evidence class, not a faster statement.** Everything ingested today is a *document*: an artifact the institution authored, styled and delivered, the thing a bank would stand behind if asked. A model reads it, introducing extraction risk the verification machinery exists to grade, but the *source* is the institution's own attestation. A feed transaction inverts both properties. There is **no extraction risk at all** — the data arrives structured with no model in the loop — but the *attestation* is weaker: the figure is an assertion by an intermediary chain with no bank-authored artifact behind it, and aggregator feeds carry their own known defects, including merchant-name rewriting, pending-transaction mutation, occasional duplicates and institution-varying sign conventions.

So documents and feeds fail in *opposite* ways: the document is strongly attested but read through a model; the feed is deterministically delivered but weakly attested. The grading vocabulary must learn that distinction rather than forcing one into the other's scale. A feed figure's provenance pointer is real but different in kind — asserted by bridge B from institution X, retrieved at time T, request R — traceable, but terminating at an intermediary's claim rather than at a page image. The instinct that direct delivery is indirectly signed off by the bank is exactly right for **OAuth-consented** connections, where the user authorized the bank to share and the bank chose to send, and *not* right for the screen-scraped share of coverage, where the bank signed off on nothing — and the connector cannot always tell which it got. The honest position: a feed figure is *evidence*, never *proof*, and the strongest thing to do with it is corroborate it against a document.

**The reconciliation opportunity converts that awkwardness into a strength.** A feed and a statement covering the same account-period are two independent witnesses to the same ground truth. Matching them deterministically produces something neither source alone can: a feed transaction later confirmed by a statement becomes the **best-graded figure in the system** — deterministically delivered *and* document-attested; a statement line the feed never showed, or a feed transaction the statement contradicts, is a *detected anomaly*, an error or a fraud that single-source products structurally cannot see; and the feed tells the product precisely what it has *not* seen, turning "measure your own incompleteness" from estimate into fact. Under that framing the feed's primary role is not more transactions — it is freshness plus corroboration for a picture whose durable substrate remains documents.

**The promises, honestly applied.** Connecting an account does not route documents through anyone's servers, and the integrated picture still exists only on-device and encrypted — but it is not true that no server sees your data: the bridge and its upstream aggregator see each connected account's transactions. That must be said plainly at the moment of consent, per connector, in words, not in a policy. The defensible claim is precise: *no additional server ever holds your assembled picture, and no server this project operates ever sees anything.* Anything stronger would be a bluff, and bluffing about privacy in a consent screen is the most corrosive possible place to do it.

Every connector is by definition a standing outbound channel, so every sync belongs in the outbound ledger: destination, time, what was requested, under which user-granted authority. New outbound bytes are a decision and never an implementation detail, so a connector framework should make that structural — a connector *cannot* be registered without declaring its outbound surface, and the declaration is what the outbound panel renders. User-initiated matters here too: a sync the user or the user's standing, visible schedule triggers is defensible under every regulatory wind; an invisible background poller is both a smell and the exact behaviour banks are now billing aggregators for.

There is no connect-all-your-accounts ceremony. Account connection arrives the way everything else does: an option, offered in context, declinable, remembered — after the third monthly statement from one institution, Viva may mention once that this account can keep itself current, and what it would cost and disclose. A decline is permanent until the user raises it. That also matches the observed reality that connection is fallible: the document path must remain first-class forever rather than becoming a neglected fallback, so a broken connector degrades to the path that always works.

The mechanisms sort cleanly against the skill bar. Paste-one-token, install-extension-and-click, and OAuth-through-your-broker sit inside "can install an app". Bring-your-own API keys do not — they are power-user paths, valuable, documented, and never on the default path. That single test is what disqualifies the best-data option as the *primary* mechanism.

## Open

- **Fork 1 — what does feed data become in the ledger?** Branch A posts feed transactions like any other measurement with a source-class-specific grade, upgraded by deterministic matching when a statement corroborates them: one ledger, no shadow state, freshness usable immediately, and the grading vocabulary already expresses differing confidence. Its cost is that feed defects become ledger events needing corrections, and the identity scheme — which keys movements partly by description — meets a source whose descriptions *change* between pulls. Branch B holds feed data in a provisional layer and posts only document-confirmed data, keeping the evidentiary story maximally clean at the price of two stores showing different truths and of never picturing an account the user connects but never uploads documents for. Branch C lets feeds only signal freshness and gaps, which discards most of the user value. The research leans A — it is what the grading vocabulary was built for, and B's two-truths problem strains the honesty promise worse than A strains identity — but A's cost is real design work on identity-under-mutation, and that work should be priced before committing.
- **Fork 2 — which mechanism ships first?** The user-pays bridge is the smallest build, an open protocol with two independent implementations so the dependency is on a protocol rather than a vendor, the ecosystem's converged choice, aligned incentives because the customer is the user, and it passes the skill bar with one pasted token — against weak investment data, no documents, a small operator and a small annual ask. Bring-your-own keys first would make the headline feature a power-user feature. Documents-first would deepen the existing strength and forgo the freshness and completeness wins for another cycle while front-loading the most expensive route to sustain. The research leans the bridge, with the cheap halves of documents-first alongside.
- **Fork 3 — is the browser extension worth building at all?** Yes only as a community-recipe platform, with the core team owning the engine and the community owning coverage; the alternative is that the watched folder plus precise nudges is honestly good enough and the project's attention goes to intelligence rather than portal maintenance. This fork does not need deciding now: build the email-trigger nudges first, and revisit with evidence about how much friction the nudged-manual path still leaves. Deferring costs nothing because it depends on nothing.
- **Fork 4 — where does connectivity live in the architecture?** A declared plugin contract makes outbound disclosure structural and lets regional mechanisms slot in without core changes, at the risk of designing a boundary against one example. Building the first connector directly into core and extracting the boundary when the second arrives is faster and better-informed — except that the *outbound-declaration* half is not speculative, since it is needed on day one for even one connector and retrofitting a trust-relevant boundary is exactly the promise-breaking rework to avoid. The research leans a deliberate middle: the outbound-declaration contract from day one, the broader plugin packaging extracted when the second connector is real.
- **The recommended sequence**, stated as a position for review rather than a decision: (1) design the evidence-class extension — how an intermediary-asserted figure is graded, keyed under mutating descriptions, reconciled against documents and upgraded — as a design doc and an ADR before it is code, since it is the one irreversible item; (2) ship the bridge client as the first connector, with the consent screen saying who sees what in words, sync appearing in the outbound ledger, and the offer surfaced in context, once, declinable and remembered; (3) ship the local email-trigger nudges and the community format registry, plus a cheap direct-connect client for the credit-union tail; (4) add brokerage-direct connectors when instrument breadth reaches investments; (5) document the bring-your-own-key power-user paths rather than building them first-class; (6) hold the browser extension as a named, undecided option; (7) parse the open-banking and tax wire formats opportunistically so any consumer export drops straight in, and track the rule rewrite, because the consumer download mandate is the piece that lands directly in the watched folder.
- The through-line to hold: the durable substrate stays documents; connections add freshness, corroboration and honest completeness measurement; every mechanism the product blesses is one the user owns and can see; and nothing on the default path requires knowing what an API key is.
