## Goal and existing behavior

A transfer link says two already posted movements are witnesses to one movement between accounts the person holds. It is an overlay: each statement’s source transactions, postings, amounts, reconciliation and provenance remain intact. A genuine live link can later justify excluding both legs from spending. This slice supplies the link evidence and state; it does not migrate the complete spending, categorization, accounting-interpretation or financial-answer read sides.

The existing implementation in `product/viva/ingest/transfers.py` settles the matching rule:

- Candidate legs have equal exact magnitude, the same currency, different accounts, eligible source/destination flow and dates within the inclusive five-day window.
- Depository and investment negative amounts are sources; nonnegative amounts are destinations. Liability negative amounts are destinations; other liability amounts are neither. Existing accepted balance-source validation already rejects zero transaction lines; do not add a different zero policy to the reused matcher.
- `is_transfer_candidate` checks the financial predicate but does not itself exclude already linked movements. The candidate loader supplies that exclusion.
- Account-identifying evidence scores two. A matching printed date adds one. The decision floor is two, so date evidence alone cannot establish ownership.
- `weigh` scores the existing graph using the existing descriptor resolver and evidence rules. `decide` requires a reciprocal unique maximum and refuses ties.
- The wrapper snapshots graph, scores, verdicts and initially open suggestions before processing sources in sorted logical movement-key order. It consumes movements as links are written; it does not repeatedly recompute verdicts and turn a previous tie into a link.
- Automatic links are corroborated. Human confirmations are verified. Their effective dates differ: automatic assertions use the later movement date, while existing manual constructors use today.

The current transfer document’s claim that candidate selection is a wholly nested scan is stale: the code already buckets destinations by currency and magnitude, then applies its predicate. This brief does not rely on that historical cost claim. SQL selection must additionally establish complete indexed dependencies and avoid loading unrelated movement history.

The existing projected overlay lives in `ledger/projection/core.py` and `ledger/projection/movements.py`. Raw assertions, live state and historical reads are different contracts, all covered below.
