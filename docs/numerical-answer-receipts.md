# Numerical answer receipts

A financial answer's figure can carry a typed numerical receipt through its
evidence route. It preserves exact decimal text, quantity, currency, date, kind,
grade and population boundary. Calculation-authored subject metadata identifies
the selected account, grouping, merchant or local goal. It is not inferred from
formatted prose or supplied as a model-selected figure.

Receipts distinguish document, movement and local-activity source identities.
They can show current-question premises with exact quoted words, recorded
starting measurements, local goal activity, calculation conventions and limits.
Hypothetical carry-forward is explicit. Local goal reservations are not bank
transfers; hypothetical and activity figures acquire no bank evidence grade.
The existing bank evidence ladder is not issuer authentication or credit proof.

The surface validates bounded typed shapes and links receipts to the current
turn's figure identities. Missing legacy receipts and invalid or unavailable
receipts remain distinguishable from ready receipts. It does not invent a
receipt from answer text. Saved turns retain receipts across reopening;
supported saved-original viewing remains a separate authenticated read.

## Saved conversation context

Every vault open, reopen or changed session starts with new-question context.
After an authoritative current Ask answer or refusal, later questions can
continue as before. Continue previous conversation additionally opts into
readable, uniquely identified saved Ask history from the loaded current-vault
conversation. It changes only the next request's context mode, preserves the
draft and focuses the question field. It does not submit, write an event,
create an answer or make a provider request.

The control requires eligible current history and a host callback. It cannot
activate while Ask is working or in accounting-explanation mode. New
conversation restores new-question context without deleting history.
Conversation text remains context rather than numerical evidence.

## Acceptance boundary

Deterministic offline browser delivery uses an isolated evaluator semantic
adapter with the real compiler, validator, executor and visible UI. It does
not qualify model interpretation, admit a runtime profile or prove signed
installation. Final measured browser and complete-gate results must bind the
candidate actually tested. The current checkpoint holds run locators;
[personal beta readiness](personal-beta-readiness.md) records release gaps.
